Flashing DEXI‑3 boards from the command line

Bootloader, PX4 firmware, and indoor‑flow params onto a DroneBlocks H743‑AIO over USB — one board with a single command, or ten back‑to‑back on a bench, with the board telling you when it's done.

For the DroneBlocks team Tool MAVLink Tool (CLI) Platform macOS Read ~6 min

The PX4 Configurator flashes a single board beautifully in a browser tab. This is its sibling for the bench: a small Python CLI that runs the same three stages — bootloader, firmware, params — but unattended and scriptable, so a production run of ten drones is plug‑in, walk‑away, repeat. One command does the whole job per board and prints a green PASS when the params verify. No QGroundControl, no STM32CubeProgrammer, no clicking.

Before you start

What you'll need

  • A Mac with the droneblocks-mavlink-tool repo cloned. The pinned firmware lives in the repo — nothing extra to download.
  • Python deps + dfu-util — the deps come from requirements.txt; dfu-util is a native tool from Homebrew (not a pip package — the one piece people forget).
  • A USB‑C data cable — not charge‑only. No battery required; USB powers the board (and the UP‑T201 flow sensor) for flashing.
The one thing to understand

Flashing is three stages, and one command runs all three: the bootloader via dfu-util (STM32 DFU), the PX4 firmware via px_uploader.py, then the DEXI‑3 params via provision_dexi3_flow.py.

Which stages does a board need? A bare/foreign board needs all three (start in DFU). A board that already runs DroneBlocks PX4 needs only firmware + params — and the tool re‑flashes it without the BOOT button, because px_uploader reboots a running app into its own bootloader. The batch tool detects which case each board is and does the right thing automatically.

Setup · once per machine

Clone and install

Clone the repo

The firmware binaries are committed, so the clone is flash‑ready.

Install the Python deps

Use uv or plain venv + pip — either creates the environment the tools run from.

Install dfu-util

One‑time, via Homebrew. Needed only for the bootloader stage, but install it now so a bare board doesn't stop you later.

Step · plug it in

Connect the board

Bare or foreign board → DFU

Unplug. Hold the BOOT button, plug in USB‑C, keep holding ~2 seconds, release. Confirm with dfu-util -l — you want 0483:df11, @Internal Flash.

Already runs DroneBlocks PX4 → just plug in

No BOOT button. The board boots its app and enumerates as /dev/cu.usbmodem*; the tool reboots it into its own bootloader to re‑flash.

Path A · one board

Flash a single board

With the board in DFU, run the orchestrator. It walks the three stages, verifies the bootloader actually enumerated (and retries a glitchy DFU write on its own), and finishes on the params check.

The benign error you'll see

dfu-util: Error during download get_status on the :leave step is a normal STM32‑DFU quirk (the chip detaches before the status read). The write succeeded as long as File downloaded successfully printed just above it.

Path B · production run

Flash a batch — ten drones, hands off

For a build run, flash_batch.py loops with zero keypresses per board: it waits for a board, detects its state, flashes it, prints a ✅ DONE line, then waits for you to unplug and insert the next. The firmware version is printed up front and on every PASS line, so the run is self‑documenting.

What it does with each board

You plug in…DetectedAction
Bare board in DFU (held BOOT)dfubootloader + app + params
Already-flashed, plugged normallyappre-flash same app + params
Bootloader-only (interrupted board)usbapp + params

The default re‑flashes the firmware on every board so the whole fleet ends up byte‑identical. Add --params-only to skip the firmware on already‑flashed boards (faster, but it trusts the existing version — fine for a re‑provision, risky for a mixed‑age batch).

After the flash

Calibrate, then verify

The flash and params are identical across boards — but sensor calibration is per‑board and can't be cloned. Before a board flies, in the PX4 Configurator /calibrate page:

  • Gyro, Level horizon, and 6‑position accel.
  • Skip the magnetometer — DEXI‑3 runs EKF2_MAG_TYPE=5 (mag off, no onboard compass).

What version am I flashing?

firmware/droneblocks-h743-aio/manifest.json is the source of truth — currently board_id 1240, firmware v1.16.2-1-g21c5f9de11. Why 1.16.2 and not 1.17: DEXI‑3 ships on the PX4 1.16 line so the FC's uXRCE‑DDS message versions match the companion px4_msgs 1.16 the rest of DEXI‑OS uses. A 1.17 FC against a 1.16 companion registers zero ROS 2 topics. Pull newer cloud builds with ./firmware/fetch-latest.sh.

When it misbehaves

Quick troubleshooting

SymptomFix
dfu-util -l shows nothingBoard isn't in DFU — hold BOOT while plugging in, then release.
Error during download get_statusBenign if File downloaded successfully printed above it — the write took.
px_uploader stuck at “Waiting for bootloader”Unplug/replug USB to catch the bootloader window; it won't flash a running app blindly.
No /dev/cu.usbmodem* after flashingOne USB power‑cycle (unplug ~5 s, replug); the MAVLink‑first tools grab the port correctly.
Connected but no sensors / dead boardRe‑seat the cable — a charge‑only cable mimics a dead board.
Don't use the web flasher mid‑runIts “port already open” bug can leave a board in the bootloader with no app; these CLI tools avoid it.
